# Fix `leave` for a daemon with a custom `--state-file`, take `leave --gossip`, find the daemons in the registry of the engine, and refuse init as a session pid

- `leave` and `session` find the daemons in the registry that the engine keeps: each running daemon has a record (pid, start time, mesh, nickname, state file) in a lock file in `<runtime base>/locks`, and a daemon runs when a process has that pid and start time. No socket is probed and no lock is taken. A daemon that was started with a `--state-file` outside the runtime base is found too; before, `leave` printed `left: []` and the daemon kept running. A stopped daemon (`SIGSTOP`) is listed. The `session` and `leave` reports no longer have the `cleaned` field.
- `leave` takes the gossip as `--gossip <id>`, as `peers`, `topology` and `poll` do. The positional form still works. Naming the gossip twice is an error.
- `leave` sends SIGTERM and then waits for the lock of the daemon, with no polling, and reports `confirmed: true` when it got the lock: the daemon has ended. A daemon that ended on the SIGTERM has removed its own socket, chunk folder and state file; a daemon that was killed in that time frees the lock too, and its files stay. `leave` and `session` remove only a tracing log that is 7 days old and has no socket, and the folder that this empties. A daemon that dies by SIGKILL leaves its socket, chunk folder and state file until the next start of the same mesh and nickname; a restart with another `--state-file` leaves the old state file until the host restarts.
- `leave`, `session` and `bell-check` refuse `--session-pid` 0 and 1, and a default that falls to init, with an error. Before, `leave --session-pid 1` stopped every daemon on the host. A command that runs from an orphaned shell (its parent is init) now fails with this error where it printed an empty list before.
- `peers --help` says that `peer_count` is the active peers plus self. The `--lookup` help and the manual say what the DHT publishes: only the beacon publishes to it, the record of a gossip with a relay lookup holds the relay URL and no IP address, and a DHT-only gossip puts the IP addresses of the beacon in the public DHT. The manual also says that a broadcast is not backfilled. The manual says why the lock files stay beside the state file and how long a stop takes.
- `peers`, `ready`, `session`, the state file and `meta get` show the stable member key of a node as `member` (`null` where no proof of it was verified), beside the `pubkey` of one run. `peers` also shows `own_member`, and `meta get` shows `members`, the member key of each slot of the document. The manual says that a restart keeps the member key and changes the `pubkey`.
- Upgrade: the member key of each node changes once at this release. A node that restarts while its old session is still in the rosters of its peers is refused as `nickname held` until that session times out.
- One daemon runs for each mesh and nickname on a host. A second start of the same pair fails at once with `another daemon already runs as <nick> on mesh <id> in this runtime folder`, and the first daemon is not touched. Before, 2 daemons of 1 nickname could run on 1 host, and the network refused the second key. The same rule holds for the library API: 2 in-process sessions of 1 nickname on 1 mesh in one runtime base are refused too.
- The state file of an agent session in the skills is named for 1 process instance, `<pid>-<start time>.json`, so a later process that gets the same pid gets another file. The new `session-file --session-pid PID` command prints the path, and the 3 skill commands call it; the line stops with an error when the process has no start time. Install the skills again with `agent-gossip plug`.
